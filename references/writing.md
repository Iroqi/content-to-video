# 第 2 步深度参考：字段规范与内容类型写法

本文件展开 SKILL.md 第 2 步的最小契约。它讲 `segments_source.json` 每个字段的完整语义与缺省兜底。它也讲几种常见内容类型怎么落进默认版式。默认版式就是槽位版式，见「字段规范」的 `layout`。写稿拿不准，查这里。

## 字段规范

**字段集是封闭的**。每一层只认本文件列出的那些键。这些层是顶层、`segments[]` 内、`segments[].dialogue[]` 每轮和 `speakers` 条目内。清单在 `_source_schema.py` 的 `SOURCE_KEYS` / `SEGMENT_KEYS` / `TURN_KEYS` / `SPEAKER_KEYS`。多写一个键，`validate_segments_source()` 就报错，并回列出本层合法清单。

为什么不留"未知键静默忽略"的余地？因为读侧全是 `.get()`。字段名拼错时，它既不生效也不报错。最坏的一类后果是**整页悄悄消失**。

例子：把 `closing` 写成 `closing_text`，结尾 agenda 卡压根不生成。这种成片的帧是两张槽位页，`check` 全绿，产物看着完全正常。所以也别拿 `segments_source.json` 当记事本写 `_note`。备注放稿件外面的文件里。

对话轮次同理只认 `speaker` / `text`。想给某一句话单独换音色是写不通的。音色只能按说话人在 `speakers` 里声明，见下文「对话字段（顶层）」。

### 段落级字段（segments[] 内）

- `id`（可选）：段落的稳定标识，用作 `images.json` 的键与配图文件名。缺省时按数组顺序取
  `seg1`/`seg2` 这样的名字，后面的段依次类推。显式 id 必须以内容段前缀 `seg` 开头。它的命名规则是字母开头，
  仅字母/数字/`-`/`_`，1–64 字符，如 `seg-openai-model`。显式 id 还要跨段唯一。`opening`/`closing`
  为结构性页保留。写稿期改顺序、删段/插段时，显式 id 让已定稿的配图不用跟着重命名。
- **`title`（必填）**：该条目的画面标题。标题要短、直接。**优先控制在一行内，最多两行**。不要把完整句子塞进标题，也不要把解释性长句或多层信息塞进标题。两画幅对超长标题的处理不同，两边都要求你写短句。**竖屏**标题区定高，超过两行的部分直接裁掉。**横屏**不钳行数，只按长度降字号。阈值与像素细节见 `references/rendering.md`「画面结构」。段落 `layout: "canvas"` 时标题根本不上画面，这两条钳制与它无关，见下。
  段落顺序就是 JSON 数组顺序，不需要在 `text` 里写"第N条"。
- **`tagline`（可选）**：标题下方小字，用于补充上下文或分类标签。标签的例子有公司/机构名、章节名和发言人。来源书名和概念分类也算。它由第 1 步整理信源时的当前对话模型直接写入。省略或留空时，pipeline 对内容段兜底为"补充阅读"。**保证画面不会因字段缺省而静默消失**。opening/closing 的 tagline 仍按顶层字段规则，缺省不显示 kicker。
- `accent`（可选，有默认值）：段落强调色。缺省按调色板顺序取，调色板定义在主题配置里。只接受 `#rgb`/`#rrggbb` 与 CSS 标准色名，例如 `red` 和 `tomato`。其它写法在契约层直接报错，包括 `rgb()`、`var()` 和拼错的色名。它会拼进成片 HTML 的三处上下文，属不可信数据。
- `layout`（可选）：段落版式。**不写 = 槽位版式**，它是标题区 + 配图槽 + verse 句子流。写 `"canvas"` = **整页画布**。整页画布下配图铺满整个画面。渲染器不生成标题层与句子流层。标题和要上画面的文字全部由配图自己画。**这不是"数据装不下才准动"的应急开关**。穿插节奏与选型判据都在 `references/image_options.md`「整页画布」，这里不复述。
  三条后果跟着这个字段。① 该段**必须有配图**。没图就只剩一条进度条的空帧，直接报错。② `title` 仍然必填，但它只喂给开屏/结尾 agenda 行。`title` **不再出现在该段画面上**，画布里的标题得你自己画。③ 该段口播**没有 HTML 字幕层**。这一层的 DOM 根本不生成。要让句子出现在画面上，就得自己画进 SVG。导演档的 `type` 与 `at` 句锚能让它跟着旁白逐拍揭示，见 `references/image_options.md`「SVG 动画：两档」。但那是你画的字，不是模板那条字幕带。这里也没有"页底固定位置"这种兜底。静音或听障观看时，这一段观众只剩画面。所以口播里的关键句务必画进图里，别让信息只存在于旁白。
  取值有两个，但**段落里你只能写 `"canvas"`**。另一个 `"agenda"` 是结构性页那一档。内容段手写它时，契约层直接报错。那页的行是从全片其它段投影出来的，不是这一段自己的文字。借过来等于在画面上印别人的目录。大小写或空格写错同样报错。静默退回槽位版式会让画里的标题和 HTML 标题同框，所以不放行。
  版式一律由 `_segments.seg_layout()` 按 `layout` 分派。渲染器不再各处按 id 猜版式。结构性页漏盖 `layout` 时，`seg_layout()` 按 id 兜回 agenda。结构性页（开屏/结尾）在稿件里是顶层字段，段落级 `layout` 够不着。它们换版式用顶层 `opening_layout` / `closing_layout`，见下文。不写 = pipeline 盖 `"agenda"`。手写 manifest 时，这两段的 `layout` 可以直接写 `"canvas"`。那一页就和内容段画布一样交给整张图。几何与对比度要求见 `references/rendering.md`「画面结构」与 `references/image_options.md`「整页画布」。
- `speed`（可选，有默认值）：段落级语速，覆盖全局 `--speed`。
- `voice_id` / `voice_style`（可选，有默认值）：内容段的音色与语气风格。它们覆盖全局
  `--voice-id` / `--voice-style`，正文换音色就靠它。`voice_id` 必须取预置音色表里的
  ID，见 `references/tts_pipeline.md`。写错直接报错。两者都参与句子音频指纹。
  改音色后，`--resume` 会重新合成受影响的句子。对话段落别在这里指定，音色归
  `speakers` 注册表按说话人管。
  opening/closing 是管线自动造的结构性页，**不支持**这两个字段。顶层也只有
  `opening_speed` / `closing_speed`，没有对应的音色键。要换开场音色就用全局 `--voice-id`。
- `text` / `dialogue`（**二选一，必填其一**）：该段的口播稿。两种形态互斥，不要同时写。
  - `text`（字符串）：单人独白。管线会自动分句。
  - `dialogue`（数组）：**双人/多人对话段落**，用 `[{speaker, text}, ...]` 按轮次交替发言。
    一问一答能还原对谈感，而不是压缩成单人讲述。要求有两条。① 顶层必须声明 `speakers`
    字典，见下文「对话字段（顶层）」。每个 `speaker` 值都要在其中。② 每轮 `text` 非空，
    且**须含至少一个可成句的字符**。纯空白或纯标点的 `text` 分句后为空，会直接报错。
    为念稿节奏计，建议每轮 `text` 都以终止标点收尾。整轮一个终止标点都没有时，管线会把
    它当成一句合成。技术上可行，但一长串不分句会拖长字幕 cue。分句规则与单句长度
    上限见下面「分句与句长」。
    ```json
    {
      "speakers": {
        "host":  {"voice_id": "茉莉", "label": "主播"},
        "guide": {"voice_id": "苏打", "label": "讲解", "voice_style": "耐心讲解，逻辑清晰"}
      },
      "segments": [
        {
          "title": "反向传播算法",
          "tagline": "深度学习基础",
          "dialogue": [
            {"speaker": "host",  "text": "反向传播听起来很复杂，能简单说说吗？"},
            {"speaker": "guide", "text": "简单说，就是把预测误差从输出层往回传，一层层告诉每个参数该怎么调整。"}
          ]
        }
      ]
    }
    ```
    一个段落里的 dialogue 轮次按顺序拼成该段的完整句子列表。字幕与时间轴共用同一序列。
    **每轮的说话人各自使用 `speakers` 里声明的音色合成语音，互不影响**。说话人信息
    只保留在 manifest 数据层。数据层存句子级 `speaker` 字段与 turns，供人工回查。这些信息不进 HTML。
    verse 画面（两画幅同样）**不渲染说话人标签**。谁在说完全靠音色切换区分。音色
    搭配与避坑判据见 `references/tts_pipeline.md` 的预置音色表。`label` 仍要照常
    声明，它存入 manifest turns。对话段落同样支持 `tagline` 和 `accent`。
- 分句与句长（`text` / `dialogue` 共用）：断句只认终止标点，逗号不切句。认哪些标点以
  `scripts/_text.py` 的 `split_sentences` 为准。中文 `。！？；`、ASCII `;` 与换行都切。
  ASCII `.!?` 需后随空白或文末，所以 `split_sentences` 不会误切小数点、`Mr.` 和 `U.S.`。
  **句长有两档，两档都不拦截。** 超过 **45 字**的一句逐句打 `[warn] 第 N 句长达 …`。它会整句
  写进一行字幕，由 CSS 折成好几行占掉句子流窗口。念出来也偏喘。落在 **32–45 字**的句子按段落
  汇总打一条 `[hint] <段 id> 有 K 句在 32–45 字 …`。32 字差不多是一条指令念完不丢主语的边界，
  所以这一档只提醒"还能再断一句"。它按段计数而不逐句刷屏。逐句刷屏会让人跳过整份日志。
  两档的根治方式相同：写稿时就在逗号处拆成两句。
  切完之后还有**反向的合并**。不足 **5 字**的片段会并到下一片段里去。它凑够 **8 字**才独立成行。
  到句尾还没凑够时，它并进上一行。`停。别动。` 是一行，`停。往左边走三步再停下。` 也是一行。短问
  `A。B。C。D。E。` 是五行标点只上一行。阈值按**字符**数，不区分中英。所以合并规则
  尤其容易吃掉中文的强调短句，两三个字的"停""就这么定"就是这样。**想让一句话独占一行字幕，它得满 5 字**。
- 上墙的一行只承载一个事实（九个字段）：这些字段会被直接印成画面上的一行，所以**不收分号**。
  写了 `；` 或 `;`，契约层当场报错，报出字段名和原文。判定在 `_validate._validate_display_text`。
  名单是两个常量，`_source_schema.ON_SCREEN_TOP_KEYS` 与 `ON_SCREEN_SEGMENT_KEYS`。
  顶层六个字段是 `title`、`opening_title`、`closing_title`。另有 `opening_tagline`、
  `closing_tagline`、`cta`。段落三个字段是 `title`、`tagline`、`takeaway`。
- 为什么只拦上墙文字：那一行的行数与列宽都是死的（见上面 `nameTrim` 与下面 agenda 行数预算）。
  分号说明两件事被挤进同一行。第二件事不是被裁掉就是被压成小字号，两种都是静默丢信息。
  **口播稿四个字段不在这一条里**：`opening` / `closing` / `text` / `dialogue` 可以写分号。
  分句器把分号当终止标点，念出来本来就是两次停顿。
- `takeaway`（可选，仅内容段有意义）：一句话要点总结，显示在**结尾 agenda 卡**的对应行。缺省时回退该段 `title`。它写比标题更凝练的那句话，也就是观众该带走的那句话。它必须是**单行**字符串。agenda 每段只占一行，含换行时契约层直接拒绝。

### 开场/结尾专用顶层字段

- `opening_layout` / `closing_layout`（可选）：把那一页从 agenda 投影卡换成**整页海报**。写 `"canvas"` 时，那一页就走内容段整页画布同一条路，满幅一张按当前画幅出的图。页面上还剩什么、连 DOM 都不生成什么，见 `references/rendering.md`「画面结构」。下面几条 agenda 字段照旧写。它们仍是数据源，只是不上那一页的画面。标题和要点得你自己画进图里。不写 = `"agenda"`。取值与门禁同段落 `layout: "canvas"`，判据见 `references/image_options.md`「整页画布」。
- `opening_title` / `closing_title`：开场/结尾 agenda 卡的大标题。`opening_title` 缺省回退到
  顶层 `title`，再缺省为"本期内容"。`closing_title` 缺省为"小结"。写稿时应按视频主题
  显式设置，如课程视频设 `opening_title: "第三章：反向传播"`。
- `opening_tagline` / `closing_tagline`：agenda 卡标题上方的等宽小字 kicker，如 `AI WEEKLY · 2026-W38`。缺省为空字符串 → 不显示 kicker。只有显式给了非空字符串才会显示。这一点与内容段落的 tagline 兜底不同。
- `cta`（可选）：结尾 agenda 卡的尾行，带 `→` 前缀。**至多一条**。内容要么是行动号召，要么是下期预告，二选一。行动号召的例子是"关注我们，每周三分钟看懂 AI"。别把它拆成两行占额度。它必须是**单行**字符串，含换行时契约层直接拒绝。缺省不显示。行数预算见下文 agenda 卡行为。
- `opening` / `closing`（口播正文）：**不写就没有这两页**。agenda 卡只在该段有口播句子时才生成。不写时成片会从第一个内容段直接开场。键名写错同样"没有这一页"，例如把结尾正文写成 `closing_text`。这一页缺省而稿件里还有 `opening_*` / `closing_*` 任何字段时，组装阶段会向 stderr 打 `[warn]`。那条 `[warn]` 点名跟着一起失效的键。看到这行先回来核对键名，别当成措辞提醒。`opening` 建议一次把"主题 + 为什么值得看"说完。`closing` 建议"回顾主线 + 一句收束"，不要戛然而止。

agenda 卡行为如下。开屏行 = 各内容段标题 + 预计时长，时长写成 `m:ss`，来自时间轴。结尾行 = 各段 `takeaway` + 至多一条 `cta` 尾行，`takeaway` 缺省回退标题。总行数有硬上限：两画幅统一 **7 行**，上限是 `_template.py` 的 `agenda.maxRows`。

超上限时**静默截断、要点优先**。先整条丢弃 `cta` 尾行。正文仍超才裁尾丢正文行。

画面上不放任何"另有 N 条"提示。四种丢弃都只向 stderr 打 `[warn]`，报清丢弃原因。四种里含两种 `cta` 无处可画：稿件根本没有 closing 段，以及作者用 `closing_layout: "canvas"` 把结尾页换成海报。所以内容段数量本身就是写稿约束：两画幅最多 7 段。≤6 段才放得下 `cta`。

agenda 行**单行不换行**。超长由两道闸处理，两道闸的表现不一样。第一道是 Python 侧 `nameTrim`，竖屏 20 字 / 横屏 26 字。它先按**字数**硬截断。切掉的那几个字直接不上画面，**也没有省略号**。这一道只在 stderr 打一条 `[warn]`，报出切掉的原文尾巴。第二道才由 CSS 补省略号。它只处理截断之后仍超出列宽的情况，那是半角/混排的实际字宽偏差。竖屏实测安全线：`takeaway` 约 17 个汉字（含数字/标点）以内，`cta` 同理。写长了先看渲染日志有没有那条 `[warn]`，再在预览里翻到结尾卡核对。

agenda 大标题（`opening_title`/`closing_title`）有长度守卫。两画幅的行数预算不同。

**竖屏**留两行余量。竖屏标题在一行容量（约 11 字）到两行容量（约 22 字）之间时，只是自然折成两行。这一段字号不动。**超过两行容量才降字号**，硬压进两行。

**横屏锁一行，不预留第二行空间**。agenda 卡行距更紧，整列预算按单行标题排。横屏标题超单行容量（约 18 字）时，立刻降字号硬压进一行。

这几处字数是按当前模板字号折算的粗估，以渲染日志为准。两者都只在**降字号**时打 `[warn]`。竖屏 12–22 字那段折行区间是安静放行的。别把"没告警"读成"没折行"。

横屏大标题超过一行容量就是肉眼可见的小字号。写稿时把它按内容段标题同样的短句标准对待。

### 对话字段（顶层）

- `speakers`（仅对话段落需要）：双人/多人对话的说话人注册表，对象格式
  `{speaker 名: {voice_id, label?, voice_style?}}`。任何段落用到 `dialogue` 时
  此字段必需，且每个 `dialogue[].speaker` 的值都要在此声明。
  - `voice_id`（必填）：该说话人使用的预设音色，取值见 `references/tts_pipeline.md` 的预置音色表。
  - `label`（可选）：说话人显示名，缺省回退为 speaker 名本身。它只写进 manifest 的
    turn 数据，画面不渲染，见上文 `dialogue` 条目。
  - `voice_style`（可选）：该说话人的语气风格描述，覆盖全局 `--voice-style`。

### 语速默认值

`opening`/`closing` 段落默认语速为 **`1.2`**（比正文段落慢一点，更像正常讲解节奏），
可用 `opening_speed` / `closing_speed` 顶层字段覆盖。正文段落未单独指定 `speed`
时跟随全局 `--speed`（倍率语义与默认值见 `references/tts_pipeline.md`）。

## 内容类型举例

### 单一段落结构

内容段不分章节 / 叙事模式。并列条目与连续叙事共用同一套版式，见 `references/rendering.md`「画面结构」。区别只在稿件本身写了什么，不必为"第几条"单独设计段落。对写稿而言只有一条：所有文字统一走 verse 句子流字幕。段内不另设正文卡 / 要点条 / 徽标。写稿时只需按内容段落组织 `segments`，承接句仍建议保持，让叙事连贯。给每段写一句 `takeaway`，它能让结尾 agenda 比复读标题更有信息量。

**全稿禁 emoji**。title、tagline、口播 text、takeaway 和 cta 一律不放。成片里 emoji 由系统字体渲染成低分辨率小图。它出现在题头位置最压质感。画面的结构语言已经有 accent 刻度条、进度条和版式层级，不需要图形点缀。想给段落贴分类标签，用 `tagline` 写文字。

#### 承接句（段落切换唯一的听觉线索）

承接句解决的是"段与段"的桥接。段落切换只有一层换页转场，它是 wipe/line，见 `references/rendering.md`「动画」。切换没有额外的视觉板块语言，听觉承接就是全部。每个内容段的第一句必须完成"从上一段到这里"的桥接。几种可用句式如下。选句式要贴内容，禁止整期视频同款句式复读：

- 回顾式：上一段讲完 X，这段从 X 的余波或对照面切入。
  `「看完 X 的发布，另一家也没闲着……」`
  `「X 的问题解决了，但代价是……」`
- 递进式：X 与 Y 是层次/因果关系时用。
  `「如果说 X 解决了"能不能"，那 Y 决定的是"好不好"……」`
- 设问式：观众此刻正想问的问题。
 「那普通用户能感受到什么变化？」「这套机制的成本在哪？」
- 场景式：直接把观众放进下一个情境。
 `「把镜头拉到用户这边……」`
 `「回到发布会现场……」`

#### 首次引入故事/案例：先铺场景，再进情节

承接句解决的是"段与段"的桥接。还有一个更隐蔽的坑在**段内部**。信源里的故事/案例
往往自带前文语境。直接摘中间最精彩的片段，观众会没头没脑。首次引入必须先用一两句
交代"人物是谁、在哪、之前发生了什么"，再进情节。

- 反例（从故事中段讲起）：`"他伸手去拿第二柄剑，没想到重达七八十斤，直接脱手……"`
  观众不知道这是谁、在哪、剑冢里一共几柄剑、第一柄发生了什么。
- 正例（先铺场景）：`"金庸笔下，剑魔独孤求败晚年埋下三柄剑。杨过来到剑冢，先取第一柄锋利的紫薇软剑，再伸手去拿第二柄……"`
  多了两句铺垫，情节就立住了。

铺垫同样只限信源里有的信息，不得为了顺溜编造前情。

### 产品评测 / 开箱解读

不按文档章节走，按"评测维度"走（外观 → 核心
体验 → 优缺点 → 总结），信源通常是用户自己写的体验笔记、或几篇测评文章的
整合。

配图：产品实拍照片能拿到就用方式 A（真实照片检索，搜产品名+型号）。讲参数对比时
用方式 C（手绘 SVG 数据图，比如跑分柱状图）。讲抽象体验感受（"上手曲线""操作逻辑"）时
用方式 B（ImageGen 意象图）。这几条路线在同一期视频里混用很常见。

### 周报 / 工作总结播报

信源是自己这一周的工作记录/项目进展，从中挑 4-6 个
值得让人（团队、老板）知道的要点，用类似新闻播报的口吻讲出来，比一段段读
文字周报更抓人。

```json
{
  "opening": "大家好，这是我这一周的工作播报。",
  "segments": [
    {"title": "XX 功能上线", "tagline": "本周进展", "text": "..."},
    {"title": "遇到的问题与解决方案", "tagline": "本周进展", "text": "..."},
    {"title": "下周计划", "tagline": "展望", "text": "..."}
  ]
}
```

数据类进展（完成率、性能提升百分比）建议配方式 C 的 SVG 数据图，比一句"提升了 30%"
配一张不相关的意象图更有说服力。

### 播客 / 视频节选摘要

精选摘要式写法：信源是一段播客转写稿或视频字幕，目标是从中挑 5-8 个最有
信息量的观点/金句意思（不是逐字复述），做成"3 分钟看完这期播客说了什么"
式的摘要视频。tagline 通常放播客名或嘉宾名。

原节目是"主持人 + 嘉宾"对谈时，用 `dialogue`（配顶层 `speakers`）比 `text`
更贴近原节目的味道，完整字段写法见上文
「段落级字段」的 `text` / `dialogue` 条目与「对话字段（顶层）」的 `speakers` 条目。

### 书评 / 影评

按"核心观点/情节脉络 → 亮点 → 局限 → 值不值得看"的
结构组织，跟产品评测的骨架很像，区别是内容偏主观赏析而不是参数对比，配图
更适合走方式 B（书封/海报风格意象图，而不是数据图）。

### 财报 / 数据报告解读

逐段完整讲解，但**这是方式 C（手绘 SVG 数据图）用得最多的场景**。每提到一个
具体数字，就配一张对应的柱状图/折线图/饼图。具体数字的例子是营收、增长率和用户占比。
不要配一张"看起来像财报"的意象图，也不要配不相关的公司照片。

```json
{
  "segments": [
    {"title": "营收同比增长", "tagline": "2026 Q2 财报", "text": "..."},
    {"title": "用户构成变化", "tagline": "2026 Q2 财报", "text": "..."}
  ]
}
```

这类数据的柱状/折线/饼环图现在都是**手绘 SVG**。`images.json` 里没有专门的数据入口，
`images/segN.svg` + 一条 `src` 映射就是全部。刻度分档、柱长比例、扇区角度要自己算并自查，
见 `references/image_options.md`「数据图的几何自查：库走了，账要自己算」。这一段要不要换成
整页画布（`layout: "canvas"`），判据见同文件「整页画布」。

### 怎么选：先看信源类型

先判断下面两个问题就够了：
1. 目标是从很多候选里**挑重点**，还是把这份材料**讲完整**？
2. 每个点要不要配真实数据（→ 方式 C）、真实照片（→ 方式 A）、抽象示意图
   （→ 方式 B/C）？选型细则见
   `references/image_options.md`。

答完这两个问题，写法就跟本文件「字段规范」与「内容类型举例」两节描述的完全一样，
不需要为每种内容类型单独学一套新规则。
