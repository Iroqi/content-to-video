# 2026-10-23 · 句尾收束：把"念完那一句"的焦点交还给下一句

上一轮（`2026-10-22-measured-sentence-span.md`）把卡拉OK的**分母**改准了，进度
落点对了。本轮接着问一个更细的问题：**一句念完之后，画面上还剩什么？**

答案是"整句全亮 accent，一动不动，直到下一次换句的那一帧被硬切走"。这是本轮
要修的那件事。

## 一、现状与前沿案例

| 观察 | 现状（改动前） | 前沿案例在做什么 |
| --- | --- | --- |
| 念完那一帧 | 整句仍是全亮 accent，一个字都不退 | Apple Music 逐行歌词：一句唱完，整句退到"已过去"那一档，只留正在唱的那句亮着 |
| 与下一句的关系 | 旧句全亮 + 新句第一个字亮 = 画面上**两个同等强度的焦点** | Spotify 同步歌词：焦点永远只有一个，旧句在下一句起来的同一拍里退干净 |
| 退的方式 | — | 逐字错峰（卡拉OK bar 收尾、bouncing-ball 歌词）：像一支笔从前往后盖过去，不是整句同时变灰 |
| 句尾留白 | 画面完全静止的空白 | 留白就是给收尾用的时长，不留白就不演 |

差别的量级不在"好看"，在**读的注意力**：观众在某句念完后仍在看那句的高亮，而
耳朵已经进入下一句了。字幕与耳不同步的那 0.3 秒，就是"字幕慢半拍"的来源。

## 二、为什么不能"整句一起压暗"

最省事的写法是 `line.style.opacity = .62`。但这在 30fps 成片里读成**闪烁**：一整
句在 0.3s 里同时变灰，人眼读到的不是"过去了"，是"这句话坏掉了"。

逐字错峰的依据是视觉上的**扫过感**：人眼对"边界正在移动"的容忍度远高于"整块
状态同时切换"。所以第 i 个字延迟 `i × (时长 ÷ 字数)`，收在句尾——最后退的正好
是刚念完的那个字。

## 三、时长从哪来：只有一处真源

收束不能占独立节拍（那样会把旁白的时间轴拉长），只能**借用句尾留白**：
「本句念完 → 下一句开口」那段空档。

这里踩了一个实打实的坑，值得写下来：

> `_subtitle_cue_spans` 返回的 `(t, end, si)`，`end` 是"cue 的终点"（= 下一句的
> **起点**），不是"这句念完的时刻"。两者只在本句没有尾静音时才重合。第一版直接
> 用 `end - t` 当留白，等于把**整句长度**当成了空档——首尾相接的稿件（每句
> `start` 差 = `duration`）算出 2.08s 留白，封顶成 0.6s，于是收束会在**句尾之前**
> 触发，逐字"倒退"盖在尚未念到的字上。

正确的留白是 `下一句开口 − 本句念完 − 换句接力`，其中"本句念完"取 `voiced`
（与运行时的 `verseEmEnd` 同一口径）。没有 `voiced` 的老 manifest 按 `end` 算，
留白恒为负 → 不演，行为与改动前逐字节一致。

拿到留白之后三条边界：

- **封顶 0.6s**：留白富余（长句之后偶尔有 1s+）不应把收束拉成慢动作；
- **地板 0.08s**：不足两帧的回落只是闪一下，退化为不演；
- **网格向下取整**（0.05s）：这个数就是留给收束的窗口，向上圆会把最后一两个字
  挤进下一句已经开口的那一帧。宁可少演 20ms，也不让两句的动作重叠。

## 四、顺手挖出来的上游 bug：字幕曾按墙钟跑

做逐帧验证时发现 `t=1.30` 就挂上了收束，而句尾在 1.55。加日志才看清：
`verseTick` 收到的时刻是 `1.533 / 1.55 / 1.567 …` **逐渐逼近 1.40 但永远不等于
1.40**，而 `tl.time()` 一直是 1.40。

根因在 `verseSync` 的"时钟锚"：

```js
const g = gsap.globalTimeline.time();
if (isFinite(g) && g + 1e-4 >= t) tt = g;   // ← 墙钟冒充时间线
```

`globalTimeline.time()` 是**墙钟**（页面打开后一直在涨）。只要它碰巧 ≥ 当前 seek
到的 `t`，就会被当成"这一帧的时刻"——于是短时间线的中后段（墙钟已超过片长）字幕
完全按墙钟跑：seek 到 1.40 却按 1.55 画。

它在成片里通常不致命（渲染器 seek 的时刻远大于墙钟，条件不成立），所以这个 bug
在仓库里躺了很久，只在**预览与短片**里显形——正是"逐帧截图验证"才能抓到的那类。
本轮把锚收回到"只信主时间线的时刻"。

## 五、验收

用 Chromium + 逐帧 seek 读回运行时状态（不是肉眼看截图）：

| 时刻 | 期望 | 实测 |
| --- | --- | --- |
| 句尾之前（1.40 / 1.55 句尾） | 未 settled，末几个字仍实色 | `cls` 无 `verse-ved-settled`，末 4 字 `1.00` |
| 句尾那一帧（1.55） | settled 挂上，逐字延迟 = `i × 0.046` | `0s / 0.046 … 0.554`，整段 13 字恰好 0.6s |
| 留白中（1.62） | 过渡正在跑，按字序递增 | `0.08, 0.14, 0.23, 0.40`（沿字序） |
| 留白末尾（1.70） | 退干净 | 全 `0.00` |
| 对照组（变量改 0s） | 逐帧与改动前一致 | 1.55 仍全 `1.00`、无 settled |

## 六、留给下一轮

- **镜头连续性**：本轮只动字幕层，与运镜完全正交。下一轮可以看"推镜时字幕层的
  视差"——目前字幕浮在相机之外，推镜时背景在动、字幕不动，长句里会读成"贴纸"。
- **收束的第二个用途**：句尾留白现在是"收束专用"。它还够放一次极轻的字距回收
  （`letter-spacing` 从 0 回到 -0.01em），让"念完"这件事在排版层也留下痕迹。
- **跨句接力**：`RELAY_SECONDS` 与收束共享同一段留白，两者顺序是硬编码的（先收
  束、后接力）。若把接力也改成"由留白推导"，两个动作可以被一段留白按比例分配。
