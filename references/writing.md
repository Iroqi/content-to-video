# 第 2 步深度参考：字段规范与内容类型写法

本文件展开 SKILL.md 第 2 步的最小契约：`segments_source.json` 每个字段的完整语义与缺省兜底，以及几种常见内容类型怎么落进默认版式（槽位版式，见「字段规范」的 `layout`）。写稿拿不准，查这里。

## 字段规范

### 段落级字段（segments[] 内）

- `id`（可选）：段落的稳定标识，用作 `images.json` 的键与配图文件名。缺省按数组
  顺序取 `seg1`/`seg2`/…。显式 id 必须以内容段前缀 `seg` 开头（字母开头，
  仅字母/数字/`-`/`_`，1–64 字符，如 `seg-openai-model`），且跨段唯一；`opening`/`closing`
  为结构性页保留。写稿期改顺序、删段/插段时，显式 id 让已定稿的配图不用跟着重命名。
- **`title`（必填）**：该条目的画面标题。标题要短、直接，**优先控制在一行内，最多两行**；不要把完整句子、解释性长句或多层信息塞进标题。两画幅对超长标题的处理不同，都要求你写短句：**竖屏**标题区定高，超过两行的部分直接裁掉；**横屏**不钳行数，只按长度降字号（阈值与像素细节见 `references/rendering.md`「画面结构」）。（段落 `layout: "canvas"` 时标题根本不上画面，这两条钳制与它无关，见下）
  段落顺序就是 JSON 数组顺序，不需要在 `text` 里写"第N条"。
- **`tagline`（可选）**：标题下方小字，用于补充上下文或分类标签（如公司/机构名、
  章节名、发言人、来源书名、概念分类等）。由第 1 步整理信源时的当前对话模型直接写入；
  省略或留空时，pipeline 对内容段兜底为"补充阅读"，
  **保证画面不会因字段缺省而静默消失**。opening/closing 的 tagline 仍按顶层字段规则，缺省不显示 kicker。
- `accent`（可选，有默认值）：段落强调色，缺省按调色板顺序取（调色板定义在主题配置里）。只接受 `#rgb`/`#rrggbb` 与 CSS 标准色名（`red`、`tomato`），其它写法（`rgb()`、`var()`、拼错的色名）在契约层直接报错——它会拼进成片 HTML 的三处上下文，属不可信数据。
- `layout`（可选）：段落版式。**不写 = 槽位版式**（标题区 + 配图槽 + verse 句子流）；写 `"canvas"` = **整页画布**：配图铺满整个画面，渲染器不生成标题层与句子流层，标题和要上画面的文字全部由配图自己画。**这不是"数据装不下才准动"的应急开关**，穿插节奏与选型判据都在 `references/image_options.md`「整页画布」，这里不复述。三条后果跟着这个字段：① 该段**必须有配图**（没图就只剩一条进度条的空帧，直接报错）；② `title` 仍然必填，但只喂给开屏/结尾 agenda 行，**不再出现在该段画面上**——画布里的标题得你自己画；③ 该段口播**没有 HTML 字幕**（画布是静态的，逐句高亮做不到），要字幕就把句子画进画布，代价是它不跟着时间轴动。取值有两个但**段落里你只能写 `"canvas"`**：另一个 `"agenda"` 是结构性页那一档，内容段手写它在契约层直接报错（那页的行是从全片其它段投影出来的，不是这一段自己的文字，借过来等于在画面上印别人的目录）；大小写/空格写错同样报错——静默退回槽位版式会让画里的标题和 HTML 标题同框，不放行。版式一律由 `_contracts.seg_layout()` 按 `layout` 分派，渲染器不再按 id 猜。结构性页（开屏/结尾）在稿件里是顶层字段、段落级 `layout` 够不着，它们换版式用顶层 `opening_layout` / `closing_layout`（见下文），不写 = pipeline 盖 `"agenda"`；手写 manifest 时这两段的 `layout` 可以直接写 `"canvas"`，那一页就和内容段画布一样交给整张图。几何与对比度要求见 `references/rendering.md`「画面结构」与 `references/image_options.md`「整页画布」。
- `speed`（可选，有默认值）：段落级语速，覆盖全局 `--speed`。
- `voice_id` / `voice_style`（可选，有默认值）：内容段的音色与语气风格，覆盖全局
  `--voice-id` / `--voice-style`——正文换音色就靠它。`voice_id` 必须取预置音色表里的
  ID（见 `references/tts_pipeline.md`），写错直接报错；两者都参与句子音频指纹，
  改音色后 `--resume` 会重新合成受影响的句子。对话段落别在这里指定，音色归
  `speakers` 注册表按说话人管。
  opening/closing 是管线自动造的结构性页，**不支持**这两个字段（顶层也只有
  `opening_speed` / `closing_speed`，没有对应的音色键），要换开场音色就用全局 `--voice-id`。
- `text` / `dialogue`（**二选一，必填其一**）：该段的口播稿，两种形态互斥，不要同时写。
  - `text`（字符串）：单人独白。会被自动分句。
  - `dialogue`（数组）：**双人/多人对话段落**，用 `[{speaker, text}, ...]` 按轮次交替发言
    （一问一答还原对谈感，而不是压缩成单人讲述）。要求：① 顶层必须声明 `speakers`
    字典（见下节），每个 `speaker` 值要在其中；② 每轮 `text` 非空且**须含至少一个
    可成句的字符**——纯空白或纯标点的 `text` 分句后为空会直接报错。
    为念稿节奏计，建议每轮 `text` 都以终止标点收尾——整轮一个终止标点都没有时会被
    当成一句合成（技术上可行，但一长串不分句会拖长字幕 cue）。分句规则与单句长度
    上限见下面「分句与句长」。
    ```json
    {
      "speakers": {
        "host":  {"voice_id": "茉莉", "label": "主播"},
        "guide": {"voice_id": "苏打", "label": "讲解", "voice_style": "耐心讲解，逻辑清晰"}
      },
      "segments": [
        {
          "title": "反向传播算法",
          "tagline": "深度学习基础",
          "dialogue": [
            {"speaker": "host",  "text": "反向传播听起来很复杂，能简单说说吗？"},
            {"speaker": "guide", "text": "简单说，就是把预测误差从输出层往回传，一层层告诉每个参数该怎么调整。"}
          ]
        }
      ]
    }
    ```
    一个段落里的 dialogue 轮次按顺序拼成该段的完整句子列表（字幕/时间轴共用同一序列），
    **每轮的说话人各自使用 `speakers` 里声明的音色合成语音，互不影响**。说话人信息
    只保留在 manifest 数据层（句子级 `speaker` 字段与 turns，供人工回查，不进 HTML），
    verse 画面（两画幅同样）**不渲染说话人标签**——"谁在说"完全靠音色切换区分，因此
    选音色尤其要避开两个音域接近的同性别音色（听感上分不清谁在说）。`label` 仍要照常
    声明（存入 manifest turns）。对话段落同样支持 `tagline`、`accent`，
    推荐搭配见 `references/tts_pipeline.md` 的预置音色表。
- 分句与句长（`text` / `dialogue` 共用）：断句只认终止标点，逗号不切句。认哪些标点以
  `scripts/_text.py` 的 `split_sentences` 为准——中文 `。！？；`、ASCII `;` 与换行都切，
  ASCII `.!?` 需后随空白或文末（所以小数点、`Mr.`、`U.S.` 不会被误切）。超过
  **45 字**的一句会打一条 `[warn] 第 N 句长达 …`（不拦截）：它会整句写进一行字幕、
  由 CSS 折成好几行占掉句子流窗口，念出来也偏喘；根治方式是写稿时就拆成两句。
- `takeaway`（可选，仅内容段有意义）：一句话要点总结，显示在**结尾 agenda 卡**的对应行；缺省回退该段 `title`。写比标题更凝练的"观众该带走的那句话"；必须是**单行**字符串（agenda 每段只占一行，含换行会被契约直接拒绝）。

### 开场/结尾专用顶层字段

- `opening_layout` / `closing_layout`（可选）：把那一页从 agenda 投影卡换成**整页海报**——写 `"canvas"`，那一页就走内容段整页画布同一条路：满幅一张按当前画幅出的图，HTML 的标题层、句子流、章节行和 `cta` 尾行全都不生成。下面几条 agenda 字段照旧写（它们仍是数据源，只是不上那一页的画面：标题和要点得你自己画进图里）。不写 = `"agenda"`；取值与门禁同段落 `layout: "canvas"`，判据见 `references/image_options.md`「整页画布」。
- `opening_title` / `closing_title`：开场/结尾 agenda 卡的大标题。`opening_title` 缺省回退到
  顶层 `title`，再缺省为"本期内容"；`closing_title` 缺省为"小结"。写稿时应按视频主题
  显式设置（如课程视频设 `opening_title: "第三章：反向传播"`）。
- `opening_tagline` / `closing_tagline`：agenda 卡标题上方的等宽小字 kicker（如 `AI WEEKLY · 2026-W38`）。缺省为空字符串 →
  不显示 kicker。只有显式给了非空字符串才会显示（与内容段落的 tagline 兜底不同）。
- `cta`（可选）：结尾 agenda 卡的尾行（`→` 前缀），**至多一条**——行动号召（如"关注我们，每周三分钟看懂 AI"）或下期预告二选一，别拆成两行占额度。必须是**单行**字符串（含换行会被契约直接拒绝）；缺省不显示。行数预算见下文 agenda 卡行为。
- `opening` / `closing`（口播正文）：**不写就没有这两页**——agenda 卡只在该段有口播句子时才生成，成片会从第一个内容段直接开场。`opening` 建议一次把"主题 + 为什么值得看"说完，`closing` 建议"回顾主线 + 一句收束"，不要戛然而止。

agenda 卡行为：开屏行 = 各内容段标题 + 预计时长（`m:ss`，来自时间轴）；结尾行 = 各段 `takeaway`（缺省回退标题）+ 至多一条 `cta` 尾行。总行数有硬上限：两画幅统一 **7 行**（`_template.py` 的 `agenda.maxRows`）。超上限时**静默截断、要点优先**：先整条丢弃 `cta` 尾行，正文仍超才裁尾丢正文行——画面上不放任何"另有 N 条"提示，四种丢弃（含"稿件根本没有 closing 段"和"结尾页被 `closing_layout: "canvas"` 换成海报"这两种 `cta` 无处可画）都只向 stderr 打 `[warn]` 报清丢弃原因。所以内容段数量本身就是写稿约束：两画幅最多 7 段（≤6 段才放得下 `cta`）。

agenda 行**单行不换行**，超长由两道闸处理，表现不一样：Python 侧 `nameTrim`（竖屏 20 字 / 横屏 26 字）先按**字数**硬截断——被切掉的那几个字直接不上画面、**也没有省略号**，只在 stderr 打一条 `[warn]` 报出被切的原文尾巴；截断之后仍超出列宽的（半角/混排的实际字宽偏差）才由 CSS 补省略号。竖屏实测安全线：`takeaway` 约 17 个汉字（含数字/标点）以内，`cta` 同理；写长了先看渲染日志有没有那条 `[warn]`，再在预览里翻到结尾卡核对。

agenda 大标题（`opening_title`/`closing_title`）有长度守卫，两画幅行数预算不同：**竖屏**留两行余量，标题在一行容量（约 11 字）到两行容量（约 22 字）之间只是自然折成两行、字号不动，**超过两行容量才降字号**硬压进两行；**横屏锁一行、不预留第二行空间**（agenda 卡行距更紧，整列预算按单行标题排），超单行容量（约 18 字）立刻降字号硬压进一行。两者都只在**降字号**时打 `[warn]`——竖屏 12–22 字那段折行区间是安静放行的，别把"没告警"读成"没折行"。横屏大标题超过一行容量就是肉眼可见的小字号，写稿时按内容段标题同样的短句标准对待。

### 对话字段（顶层）

- `speakers`（仅对话段落需要）：双人/多人对话的说话人注册表，对象格式
  `{speaker 名: {voice_id, label?, voice_style?}}`。任何段落用到 `dialogue` 时
  此字段必需，且每个 `dialogue[].speaker` 的值都要在此声明。
  - `voice_id`（必填）：该说话人使用的预设音色，取值见 `references/tts_pipeline.md` 的预置音色表。
  - `label`（可选）：说话人显示名，缺省回退为 speaker 名本身；只写进 manifest 的
    turn 数据，画面不渲染（见上文 `dialogue` 条目）。
  - `voice_style`（可选）：该说话人的语气风格描述，覆盖全局 `--voice-style`。

### 语速默认值

`opening`/`closing` 段落默认语速为 **`1.2`**（比正文段落慢一点，更像正常讲解节奏），
可用 `opening_speed` / `closing_speed` 顶层字段覆盖。正文段落未单独指定 `speed`
时跟随全局 `--speed`（默认 1.5）。

## 内容类型举例

### 单一段落结构

内容段不分章节 / 叙事模式（并列条目与连续叙事共用同一套版式，见 `references/rendering.md`「画面结构」），区别只在稿件本身写了什么——不必为"第几条"单独设计段落。对写稿而言只有一条：所有文字统一走 verse 句子流字幕，段内不另设正文卡 / 要点条 / 徽标。写稿时只需按内容段落组织 `segments`，承接句仍建议保持、让叙事连贯。给每段写一句 `takeaway` 能让结尾 agenda 比复读标题更有信息量。

#### 承接句（段落切换唯一的听觉线索）

段落切换只有一层 cross-fade，没有额外的视觉板块语言，听觉承接就是全部——每个内容段的第一句必须完成"从上一段到这里"的桥接。几种可用句式（贴内容选，禁止整期
视频同款句式复读）：

- 回顾式：上一段讲完 X，这段从 X 的余波或对照面切入。
  「看完 X 的发布，另一家也没闲着……」「X 的问题解决了，但代价是……」
- 递进式：X 与 Y 是层次/因果关系时用。
  「如果说 X 解决了"能不能"，那 Y 决定的是"好不好"……」
- 设问式：观众此刻正想问的问题。
 「那普通用户能感受到什么变化？」「这套机制的成本在哪？」
- 场景式：直接把观众放进下一个情境。
 「把镜头拉到用户这边……」「回到发布会现场……」

#### 首次引入故事/案例：先铺场景，再进情节

承接句解决的是"段与段"的桥接；还有一个更隐蔽的坑在**段内部**：信源里的故事/案例
往往自带前文语境，直接摘中间最精彩的片段，观众会没头没脑。首次引入必须先用一两句
交代"人物是谁、在哪、之前发生了什么"，再进情节。

- 反例（从故事中段讲起）："他伸手去拿第二柄剑，没想到重达七八十斤，直接脱手……"
  ——观众不知道这是谁、在哪、剑冢里一共几柄剑、第一柄发生了什么。
- 正例（先铺场景）："金庸笔下，剑魔独孤求败晚年埋下三柄剑。杨过来到剑冢，先取
  第一柄锋利的紫薇软剑，再伸手去拿第二柄……"——多了两句铺垫，情节就立住了。

铺垫同样只限信源里有的信息，不得为了顺溜编造前情。

### 产品评测 / 开箱解读

不按文档章节走，按"评测维度"走（外观 → 核心
体验 → 优缺点 → 总结），信源通常是用户自己写的体验笔记、或几篇测评文章的
整合。

配图：产品实拍照片能拿到就用方式 A（真实照片检索，搜产品名+型号）；讲参数对比时
用方式 C（手绘 SVG 数据图，比如跑分柱状图）；讲抽象体验感受（"上手曲线""操作逻辑"）时
用方式 B（ImageGen 意象图）。这几条路线在同一期视频里混用很常见。

### 周报 / 工作总结播报

信源是自己这一周的工作记录/项目进展，从中挑 4-6 个
值得让人（团队、老板）知道的要点，用类似新闻播报的口吻讲出来，比一段段读
文字周报更抓人。

```json
{
  "opening": "大家好，这是我这一周的工作播报。",
  "segments": [
    {"title": "XX 功能上线", "tagline": "本周进展", "text": "..."},
    {"title": "遇到的问题与解决方案", "tagline": "本周进展", "text": "..."},
    {"title": "下周计划", "tagline": "展望", "text": "..."}
  ]
}
```

数据类进展（完成率、性能提升百分比）建议配方式 C 的 SVG 数据图，比一句"提升了 30%"
配一张不相关的意象图更有说服力。

### 播客 / 视频节选摘要

精选摘要式写法：信源是一段播客转写稿或视频字幕，目标是从中挑 5-8 个最有
信息量的观点/金句意思（不是逐字复述），做成"3 分钟看完这期播客说了什么"
式的摘要视频。tagline 通常放播客名或嘉宾名。

原节目是"主持人 + 嘉宾"对谈时，用 `dialogue`（配顶层 `speakers`）比 `text`
更贴近原节目的味道，完整字段写法见上文
「段落级字段」的 `text` / `dialogue` 条目与「对话字段（顶层）」的 `speakers` 条目。

### 书评 / 影评

按"核心观点/情节脉络 → 亮点 → 局限 → 值不值得看"的
结构组织，跟产品评测的骨架很像，区别是内容偏主观赏析而不是参数对比，配图
更适合走方式 B（书封/海报风格意象图，而不是数据图）。

### 财报 / 数据报告解读

逐段完整讲解，但**这是方式 C（手绘 SVG 数据图）用得最多的场景**：每提到一个
具体数字（营收、增长率、用户占比），配一张对应的柱状图/折线图/饼图，而不是
配一张"看起来像财报"的意象图或不相关的公司照片。

```json
{
```

这类数据的柱状/折线/饼环图现在都是**手绘 SVG**：`images.json` 里没有专门的数据入口，
`images/segN.svg` + 一条 `src` 映射就是全部。刻度分档、柱长比例、扇区角度要自己算并自查，
见 `references/image_options.md`「数据图的几何自查：库走了，账要自己算」；这一段要不要换成
整页画布（`layout: "canvas"`），判据见同文件「整页画布」。

### 怎么选：先看信源类型

先判断下面两个问题就够了：
1. 目标是从很多候选里**挑重点**，还是把这份材料**讲完整**？
2. 每个点要不要配真实数据（→ 方式 C）、真实照片（→ 方式 A）、抽象示意图
   （→ 方式 B/C）还是有真正的连续过程（→ 方式 D）？选型细则见
   `references/image_options.md`。

答完这两个问题，写法就跟本文件「字段规范」与「内容类型举例」两节描述的完全一样，
不需要为每种内容类型单独学一套新规则。
